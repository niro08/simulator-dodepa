# Технические риски: предыстория «Стример»

- **Автор:** Technical Director · 2026-09-27 · v1
- **Статус:** записка фазы D (задача 2 из `design/streamer-prequel-vision.md` §9). Кода нет. ADR ниже — черновые, статус «Предложено».
- **Вход:** `design/streamer-prequel-vision.md`, `production/architecture.md`, текущий код `src/game/**`, `src/stores/game.ts`, `src/components/ui/Ticker.vue`, `src/components/game/GameShell.vue`, `src/i18n/ru.test.ts`.
- **Не зависит от GDD** (`design/gdd-streamer-prequel.md` пишется параллельно). Всё, что зависит от чисел и правил GDD, помечено **[GDD]**. Решения здесь должны выдержать любой ответ GDD: 14 или 28 дней, 4 или 6 спонсоров, есть разрыв контракта или нет.

## 0. Вердикт

**Технически режим реализуем, блокеров нет.** Ядро чистое, RNG инжектируемый, у сейва уже есть цепочка миграций v0→v3, события сна идут через общий pipeline эффектов. Всё это как раз нужно второму старту.

Три главных риска (подробности в §7):
1. **Базовый ран «поплывёт» незаметно.** Лишний вызов `rng` в общей ночи, спонсорские карточки в общем пуле или новая концовка в `ENDING_IDS` меняют исходы или коллекцию у текущих игроков. Митигация: **golden-тест базового рана до первой строки кода** и изоляция режима по `run.mode`.
2. **Чат ломает детерминизм и спойлерит спин**, если берёт числа из `run.rngState` или реагирует на событие спина раньше, чем остановились барабаны (ADR-001: «результат сначала, анимация потом»).
3. **QA-09 сейчас проверяет только тикеры и 7 слов.** Чат, спонсоры и донаты — основная масса новых строк, и брендовый стоп-лист их не видит.

## 2. Второй старт в `RunState` и миграция сейва

### 2.1 Варианты формы

| | A. `mode` + под-объект **(рекомендую)** | B. Размеченное объединение типов | C. Флаги в `run.flags` |
|---|---|---|---|
| Суть | `run.mode: 'base' \| 'streamer'`, `run.streamer: StreamerState \| null` | `type RunState = BaseRun \| StreamerRun` с дискриминатором `mode` | `flags.streamer = true`, числа в `stats` |
| Плюсы | Общий код не меняется. Состояние стримера в одном месте: зрители, контракты, пик, рефералы. Тот же приём, что `eventState` в v3 | Типы сами не пустят к `streamer` в базовом ране | Ноль миграции |
| Минусы | Нужна дисциплина: `run.streamer` может быть `null`, геттер-хелпер обязателен | Сужение типа нужно в каждом из ~15 модулей ядра и в сторе. Большой дифф ради гарантии, которую даёт хелпер | `flags` — `Record<string, boolean>`, контракты и счётчики туда не лягут. Нетипизировано |
| Обратимость | Высокая | Средняя | — |

Рекомендация A. Эскиз для ADR, не код:

```ts
type RunMode = 'base' | 'streamer'
interface RunState { /* …как сейчас… */ mode: RunMode; streamer: StreamerState | null }
interface StreamerState {       // форма уточняется по GDD
  viewers: number; peakViewers: number
  contracts: SponsorContract[]  // id, день начала, выполнено ли условие, накопленная цена
  donationsTotal: number
  referrals: { signedUp: number; lost: number; returnedNextDay: number }
  nickSeed: number               // ник стримера генерируется из seed, строка не хранится
}
```

### 2.2 Конфиг режима **[GDD]**

`ctx.config` сейчас глобальный. Если GDD выберет 14 дней или другой старт, режиму нужен свой `balance` (`RUN_DAYS`, `BILLS`, `START_*`). Решение: `resolveConfig(base, mode)` → `GameConfig` вызывается в `dispatch`, `createRun` и **в `validateRun`**. Последнее обязательно: `maxRunDay()` и `validateBills()` клампят день и счета по `config.balance`, и 14-дневный сейв без этого провалидируется по 28-дневным правилам.

Инвариант economy-v1 §12 фиксируем тестом: патч режима не может содержать `slot`, `BONUS_*`, `TILT_*`. `expectedRtp(resolveConfig(c, 'streamer').slot) === expectedRtp(c.slot)`.

### 2.3 Миграция v3 → v4

- `migrateV3toV4`: `{ ...data, version: 4 }`. Ран переносится как есть, `validate` дописывает `mode: 'base'`, `streamer: null`. Профиль получает новые поля с дефолтами (§3). Это тот же приём, что v2→v3, риск низкий.
- `validateRun`: `mode = oneOf(x.mode, ['base','streamer'], 'base')`. Если `mode === 'streamer'`, а `streamer` битый, **не** превращаем ран в базовый: подставляем `freshStreamerState()`. Режим — это идентичность рана, и молча его менять нельзя.
- В `cloneRun` нужно глубокое копирование `streamer.contracts`. Иначе мутация draft утечёт в предыдущее состояние, а Pinia увидит одну и ту же ссылку. Тест: мутация клона не меняет оригинал.
- `applyInvariants`: `viewers ≥ 0`, целые, `peakViewers ≥ viewers`.
- Новые `GameEvent` (`viewersChanged`, `donation`, `sponsorOffered`, `contractSigned/Broken/Violated`, `chatReacted`?) нужно добавить в `EVENT_TYPES` в `validate.ts`. Там стоит `satisfies Record<GameEventType, true>`, так что компилятор заставит это сделать. Иначе события молча отфильтруются из хроники при загрузке.
- Фикстуры в `save.test.ts`: v3 с активным раном → v4 с `mode: 'base'`; v4 streamer round-trip; v4 streamer с битым `streamer`; сейв v5 «из будущего» — только чтение (механизм уже есть).
- **Откат билда в Steam.** Игрок на v4 откатывается на билд с v3 → сейв «из будущего», режим «только чтение». Уже работает (ADR-008), но в release notes нужно предупреждение.

### 2.4 Концовки режима — отдельный риск

`EndingId` — одно объединение. `ENDING_IDS` определяет коллекцию, `ALL_ENDINGS` (Steam API Name, после релиза не меняется) и тест `day.test.ts`, который ждёт ровно 7 концовок. Если просто добавить `channel_deleted` и `ambassador`:
- у игроков с 7/7 полоска `ALL_ENDINGS` станет 7/9, а смысл Steam-ачивки поменяется после релиза;
- «остальные концовки те же, тексты свои» (vision §4) — значит, `jail` в стримере и `jail` в базе должны различаться хотя бы в текстах и в коллекции.

**Рекомендация (ADR-012):** концовка = пара `(mode, endingId)`. Базовый `ENDING_IDS` не трогаем. У стримера свой список `STREAMER_ENDING_IDS`: общие id плюс два своих. `profile.endings` оставляем для базы, добавляем `profile.streamerEndings`. `ALL_ENDINGS` считает только базу, для приквела — отдельная ачивка. Тексты: `ENDINGS[mode][id]`.

Две точки, где ядро предлагает `referral` (`commands/slot.ts:87`, `day.ts:423`), закрываются по `mode`: в стримере на их месте `ambassador` **[GDD]**. Нужен тест: в режиме стримера `referral` не наступает никогда.

### 2.5 Профиль, статистика, история

- `RunSummary` получает `mode`, иначе «История ранов» смешает режимы.
- Lifetime-статистика: `reduceStats` одна на оба режима. **[решение владельца]**: считаем ли спины стримера в `profile.stats`? Рекомендую **да** (это тот же игрок и те же проигранные деньги), но run-scope ачивки базового рана (`ENDING_*`, серийные) из стримера не выдаём. Косметика экономики не меняет, так что П5 это не нарушает. Нарушает ожидание Steam-ачивки «концовка основной игры».
- Одна ячейка активного рана. Старт приквела при активном базовом ране = `abandonRun` по существующей семантике. UI-подтверждение уже есть (`MENU.confirmTitle`).

## 3. Мета-флаг в профиле

Отдельного `dodepaMeta` нет, флаги пишем в `Profile`. Принцип: **хранить только то, что нельзя вывести.**

| Нужно | Хранить или выводить | Как |
|---|---|---|
| Режим открыт (после первого рана с любой концовкой) | **Выводить** | `Object.values(profile.endings).some(e => e.count > 0)`. Миграция не нужна: у ветеранов режим откроется сам. Брошенный ран (`abandoned`) не считается — так и задумано |
| Альтернативное вступление («ты уже видел…») | **Выводить** | `profile.endings.referral?.count > 0` |
| Строка «по приглашению от @ник» на баннере бонуса | **Хранить** | `profile.prequel: { completedAt: number; nickSeed: number } \| null`. Ник строится из `nickSeed` словарём i18n при показе. Строку ника не храним: в en-локали будет свой ник, и в сейве нет пользовательского текста |
| «Начать его четыре недели» | Не флаг | Команда стора: `recordRunEnd` приквела → `createRun(config, seed, now, { mode: 'base', intro: 'referral_38' })`. Интро — флаг рана, не профиля |

Риски:
- **Флаг нельзя класть в `localStorage['dodepa.ui']`** (как calm у `useTheme`): он не попадает ни в сейв, ни в бэкап, ни в Steam Cloud, и его никто не валидирует.
- Строка на баннере — косметика Витрины. Тест: `profile.prequel` не читается ни одной функцией `src/game/**`, кроме геттеров вида (П5: без экономического эффекта). Проверяется grep-тестом по образцу `purity.test.ts`.

## 4. Детерминизм RNG

Сейчас весь ран живёт на одном потоке `rngState`, и порядок вызовов — часть контракта сейва и баланса.

**Правила (ADR-013):**
1. **Игровые механики стримера** (прирост зрителей, если он случайный, суммы донатов, выбор спонсорской карточки) берут `ctx.rng`, как всё ядро. Это честная часть рана, она сохраняется и защищена от save-scum.
2. **Чат — презентационный слой и `rngState` не трогает никогда.** Реплики, ники и порядок строятся чистой функцией от `(run.seed, logEntry.id, variant)` через хэш (как `ParticleBurst.vue`: хэш индекса, без `Math.random`). Следствия:
   - правка пула реплик писателем не меняет исходы спинов и не ломает баланс-тесты;
   - после перезагрузки чат тот же;
   - чат не хранится в сейве, он выводится из хроники (`run.log`, лимит 50) и `run.streamer`.
3. **Базовый ран побайтно не меняется.** Новый код в общих функциях (`runNight`, `wake`, `endDay`, спин) выполняется только под `if (run.mode === 'streamer')` и **после** всех существующих вызовов `rng`. Спонсорские карточки лежат в отдельном пуле режима, не в `config.events.pool`. Иначе `eligibleSleepEvents` и сумма весов начнут зависеть от нового контента, пусть и через `when`.
4. **Golden-тест (делать первым, до любой правки ядра).** Для ~20 seed × 3 стратегий из `strategies.ts` на `main` записать хэш `(финальный RunState, лог событий)` в фикстуру. После каждого PR приквела хэши совпадают. Это и есть проверяемое условие «базовый ран побайтно не изменился» из задачи 9.
5. **Спойлер спина.** Стор коммитит событие `spin` до анимации (ADR-001). Если чат подписан на события стора, он напишет «ЗАНОС!!!» раньше, чем остановятся барабаны. Реакции чата на `spin` показываются только после `revealPending()`. Нужен тест стора: до reveal чат-вид не содержит реакций на последний спин.

## 5. i18n-тесты и бренд-бан (QA-09)

Что есть: `ru.test.ts` через `satisfies { [K in GameEventType]: … }` заставляет покрыть текстом каждое новое событие — хорошо, работает само. QA-09 — узкий регэксп только по тикерам.

Что нужно (для qa-lead, задача 7, и writer, задача 11):
1. **Общий стоп-лист** в одном модуле (например, `src/i18n/stoplist.ts`, данные): текущие 7 + С1 (Kick, Twitch, Trovo, VK Play, Rutube, GoodGame, DonationAlerts, Boosty) + кириллические написания и транслит. Короткие слова вроде «кик» проверять по границе слова, иначе будут ложные срабатывания («кикнули из чата»).
2. **Обход всех строк**, а не только тикеров: рекурсивно по экспортам `ru.ts`, `ui.ts` и пулу чата; функции вызываются с тестовыми аргументами. Один тест на все пулы — новый пул спонсоров не выпадет из проверки.
3. **Гард ссылок и промокодов (анти-пиллар «реальные ссылки»):** нет `https?://`, `www.`, доменов кроме зоны `.нет`, `t.me/`, `@`-хэндлов реальных форматов. Промокоды — только из белого списка абсурдных (`ДОЛГ_НАВСЕГДА`).
4. **Маска ников С2:** генератор выдаёт только `слово_слово_цифры` (регэксп). Плюс небольшой денилист ников, которые writer и qa-lead сочтут узнаваемыми. Автотест не докажет, что ник не совпадает с реальным, это остаётся ручной проверкой из С1.
5. **Пара у каждой строки:** реплики чата и спонсорские интеграции хранятся структурой `{ v, i }` (как `formatAchievementToast`), тест требует непустую Изнанку у каждой. Так правило §6 «у каждой Витрина-строки есть пара» проверяется автоматически.
6. Вне автотестов: С3, С6 (нет несовершеннолетних), «вырежи из контекста». Это чек-лист qa-lead.

Локализация: сейчас только `ru`. Пул чата (~60 пар) и генератор ников умножат стоимость en-локали (TD-20). Словари ников держать в i18n, не в ядре.

## 6. Чат-лента: где встраивается, производительность, reduced-motion

**Где.** `GameShell.vue` показывает два тикера: верхний неоновый «LIVE-ВЫИГРЫШИ» (`topTicker`, в Изнанке — честные пары) и нижний бумажный «А тем временем» (`bottomTicker`). «Чат вместо ленты заносов» — это **верхний** слот `.gs__ticker`, условие `hud.mode === 'streamer'`. Нижняя честная лента остаётся (или становится «Изнанкой чата» **[UX, задача 5]**).

**Чат — не вариант `Ticker.vue`.** Ticker — горизонтальная бегущая строка с дублированной копией для бесшовной прокрутки и высотой 32–36 px. Чат — вертикальный поток с добавлением снизу. Нужен новый компонент (`ChatFeed.vue`), у него общие с Ticker только пауза и поведение в reduced-motion. Растягивать Ticker под два режима значит сломать его текущие 3 места использования.

**Бюджет производительности** (сверить с TD-26):
- В DOM не больше **40 сообщений** (кольцевой буфер), виртуализация не нужна.
- Видимый темп — не чаще одного сообщения в ~300–500 мс. **Всплески агрегируются:** «ДОДЕП ВСЁ» → 140 сообщений превращаются в 5–8 видимых строк плюс «…и ещё 132». Кстати, это и шутка Изнанки №9 из vision.
- Один планировщик (`setInterval` или rAF) на компонент, а не таймер на сообщение. Пауза при `document.hidden`.
- Анимации только `transform`/`opacity`. Никакого `scrollTop`-анимирования в цикле. `contain: content` на ленте.
- Не перехватывать скролл: если игрок прокрутил вверх, автопрокрутка останавливается.
- Проверка на Deck/слабом ноутбуке в рамках TD-26: при спине и всплеске чата fps слота не падает ниже порога.

**Reduced-motion и доступность:**
- Источник — только `useTheme().motionReduced`. В этом режиме нет слайдов и прокрутки: пакетное обновление раз в N секунд (как статичный Ticker раз в 6 с) плюс кнопка паузы (требование CD-21, как у Ticker).
- **`aria-live` на весь чат — нельзя:** спам затопит скринридер. Лента `aria-live="off"`. Отдельный вежливый анонсер только для ключевых строк (мама в чате, донат, спонсор), не чаще раза в несколько секунд.
- Донат-алерты и хорны: не больше 3 вспышек в секунду (WCAG 2.3.1), в reduced-motion вспышек нет совсем.
- «Робот зачитывает донат» (vision, шутка 3): **не делать через `speechSynthesis`**. Голоса различаются между Windows, Linux и Deck, в Electron их может не быть вовсе. Только заранее подготовленный звук или SFX-пресет (audio-director, задача 12).

## 9. Оценка по частям

Шкала: **S** ≤ 1 дня, **M** 2–4 дня, **L** 1–2 недели (реализация + тесты + ревью одним исполнителем). Ориентир для producer (задача 8), не обязательство. Все оценки после одобрения GDD, кроме golden-теста.

| Слой | Часть | Оценка | Зависит от |
|---|---|---|---|
| Тесты | Golden-тест базового рана (§4.4) — **сделать первым** | S | — |
| Сейв | v4: миграция, `validateRun`/`validateProfile`, фикстуры | S | ADR-011 |
| Ядро | `mode`, `StreamerState`, `createRun` с режимом, `cloneRun`, инварианты, `resolveConfig` | M | ADR-011 |
| Ядро | Зрители: источники и стоки, события | M | GDD, числа (4) |
| Ядро | Спонсоры: карточки в пуле режима, контракты, условия, разрыв, неустойка | **L** (M при фолбэке «без разрыва, 4 спонсора») | ADR-014, GDD, числа |
| Ядро | Концовки режима, коллекция, ачивки, гейт `referral` | M | ADR-012 |
| Ядро | Мета-флаг, открытие режима, переход в базовый ран | S | ADR-015 |
| Ядро | Строки Выписки стримера (`statement.ts`) | S | GDD |
| Ядро/i18n | Генератор чата (чистый, хэш, агрегация всплесков) | M | ADR-013, пилот writer (3) |
| Стор | Команды режима, отложенные реакции чата до reveal, переход между ранами | S–M | ядро |
| UI | `ChatFeed.vue`: лента, пауза, reduced-motion, a11y, мобильная версия | M–L | UX (5), арт (6) |
| UI | Экран выбора старта, карточка спонсора, счётчик 👁, баннер «по приглашению» | M | UX (5) |
| Тесты | Общий стоп-лист, гард URL и промокодов, пары `{v,i}`, маска ников | S | задача 7 |
| Инструменты | Стратегии стримера в `strategies.ts` + тест доли побед | M | числа (4) |
| **Итого** | | **≈ L × 2–3**: порядка 4–6 недель одного программиста или 2–3 недели при параллели ядро / UI / контент | |

Самый дорогой и самый урезаемый кусок — **контракты спонсоров**. Фолбэк из vision (без разрыва, 4 спонсора) экономит примерно неделю: ADR-014 сводится к «контракт до конца рана».

## 10. Вопросы, которые нужно закрыть до фазы I

1. **[решение владельца]** Спины и деньги стримера идут в lifetime-статистику профиля? Рекомендую да, но без выдачи базовых ачивок концовок (§2.5).
2. **[GDD]** Длина рана (14/28) и есть ли «Ещё неделю» у стримера — влияет на `resolveConfig` и валидацию.
3. **[GDD]** Зрители — детерминированная формула или случайный прирост? Детерминированная проще тестировать, и её легче доказать для R-09.
4. **[UX]** Нижняя лента «А тем временем» в режиме стримера остаётся или становится Изнанкой чата?

**Поймём, что решения верные, если:** golden-хэши базового рана совпадают на всех PR приквела; правка пула реплик чата не меняет ни один баланс-тест; `ALL_ENDINGS` у существующего сейва показывает прежний прогресс; сейв v3 с активным раном грузится без уведомлений; QA-09 падает, если вставить «Twitch» в любую строку игры.
